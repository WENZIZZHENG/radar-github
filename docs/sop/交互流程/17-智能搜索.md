# §17 智能搜索（T-034 追加；T-036 追问与扩量修订，v2.9，2026-08-19 本人确认）

> 需求来源：2026-08-18 本人提出——做爬虫/桌面端/Java 项目时，想用自然语言搜出对应项目推荐；家底：池内 3024 仓（≥1000 星），主流语言够厚（Python 556/TS 543/Rust 264/Go 243/C++ 229），薄区（Java 131/C# 90/Kotlin 58）与未达千星的新生长尾由池外实时补搜覆盖。T-036（2026-08-19 grilling 共识）：搜索结果支持追问式进一步筛选，结果数量 10→20；同日追加拍板：意图契约扩结构化筛选条件白名单（filters，第一版＝创建时间＋星数下限）＋"暂不支持"回显。技术方案见 OpenSpec change `smart-search`（已归档）与 `search-follow-up`。
> 组件分档：输入框/按钮/徽标/结果行全复用既有冻结视觉体系组件（结果行＝榜单行组件），无新视觉元素，免示意图（2026-08-09 分档口径）。

### 17.1 元素与位置
- 新页面 P8 `/search`：顶部大输入框＋提交按钮＋结果列表；顶栏加"搜索"项（**顶栏上限由 5 调整为 6**，本次拍板）。
- 结果区顶部**意图透明行**："理解为：关键词1、关键词2 …／语言：…"（LLM 解析结果如实展示，可纠错可预期）；追问后该行显示**当前生效的合并意图**。筛选条件生效时同行展示（"创建：近 1 年内"／"星数 ≥5000"形态）；LLM 无法支持的条件（如"最近一周有提交"——池内无 pushed_at 数据）如实展示"暂不支持：…"，仅展示不影响检索。
- 结果行复用榜单行组件（紧凑行＋详情默认展开），行下多一句中文推荐理由（≤50 字，"为什么适合你的意图"视角）；**池外结果带"池外"徽标**（无增星/译文/概要，展示 GitHub 原始描述），行尾带关注星。
- 空结果：如实说明形态——"没有找到匹配「已理解的关键词/语言」的项目，换个说法试试？"（措辞以实现时定稿为准），不硬编任何条目。追问搜空的处置见 §17.2 第 6 步与 §17.3。
- 单输入框复用：首搜与追问共用结果页顶部同一输入框，无单独"追问框"、无轮次历史记录；结果页同一框提交即视为追问，全新搜索经导航入口进入（GET 页不带上轮字段）。

### 17.2 主路径逐步序列
1. 输入自然语言（如"我要做爬虫，Python 的"）→ 提交 → 加载态提示（秒级）。
2. LLM 意图理解：产出**多个关键词 × 多个语言**（及主题词，不锁单个）；结构化条件进 filters 白名单字段（如"创建时间 1 年内"→created_within_days=365），不支持的条件进 unsupported 回显 → 意图透明行展示。
3. 池内召回候选（约前 50；filters 生效时叠加 SQL 真过滤：创建时间距今 <N 天／最新星数 ≥N）→ LLM 按匹配度精选 **20 条**＋各写一句推荐理由。
4. 池内不足 20 条 → 同组关键词实时 GitHub Search 补搜（filters 映射为 created:>/stars:>= 限定词），补足 20 条为止；池内在前、池外在后。
5. 池外行点关注星 → 该仓动态入池（决策 9 链路），次日起有基线快照、增星、进翻译队列。
6. **追问（T-036）**：在结果页同一输入框继续输入补充/修正条件（如"只要异步的""换成 Go 的""放宽到 3 年内"）→ 提交时前端把上一轮意图随新输入一并回传 → LLM 合并产出新意图（filters 同名覆盖、未提及保留；意图透明行更新为合并后意图）→ 用新意图重跑第 3~4 步，**结果整体替换**。追问搜空（池内＋池外全空）：结果区不清空——顶部如实说明并展示新旧意图对比，上一轮结果保留在下方。

### 17.3 分支与异常
| 场景 | 走向 |
|---|---|
| DeepSeek key 未配置/鉴权失败 | 搜索页明确提示"搜索暂不可用（AI 未配置）"；榜单等主链路不受影响 |
| LLM 意图理解返回非法 JSON | 退化为以原输入作单一关键词的池内检索，不报错页 |
| LLM 意图合并返回非法 JSON | 同上退化口径：以本轮新输入作单一关键词检索（不沿用旧意图） |
| LLM 产出白名单外 filters 字段或类型非法 | 丢弃该字段记 WARNING，其余合法 filters 照常生效，不报错页 |
| LLM 精选失败（非法返回/超范围引用） | 按粗排顺序直出池内候选（至多 20 条，无推荐理由），记 WARNING |
| GitHub Search 失败/限速/token 缺失 | 跳过补搜：只出池内结果，池外区标注"补搜失败"或不渲染 |
| 池内＋池外全空（首搜） | 如实空结果说明（§17.1），无任何编造条目 |
| 池内＋池外全空（追问） | 如实说明＋新旧意图对比，上一轮结果保留在下方（§17.2 第 6 步） |
| 上一轮意图回传缺失/非法 | 按首搜处理（无状态口径，报错页不出现） |

### 17.4 服务端口径（钉死）
- 三段式链路：LLM 只做意图理解与精选润色，**检索在本地 SQL / GitHub API 做**——候选集永远来自真实数据，LLM 无幻觉出不存在项目的机会；精选时 LLM 只许从候选清单中按编号选择。
- 池内召回：alive 仓按关键词组匹配（全名/英文描述/topics 任一命中任一关键词计一次），语言过滤取交集；粗排＝命中数降序 → 最新星数降序，取约前 50。
- **filters 白名单**：LLM 只许产出白名单字段（第一版 `created_within_days` int／`min_stars` int），服务端逐字段校验（白名单外或类型非法 → 丢弃记 WARNING）；池内映射：创建时间 → `github_created_at` 非 NULL 且距今 <N 天（NULL 不进，与新项目区同口径）、星数下限 → 最新快照星数 ≥N；池外映射：`created:>YYYY-MM-DD`／`stars:>=N` 限定词（不占单查询 5 个布尔运算符预算）。白名单外条件进 `unsupported` 仅展示。扩白名单＝prompt 示例＋服务端校验＋SQL 过滤＋限定词映射四处对齐的小改动。
- 精选：至多 20 条按匹配度排序；不足 20 条有几个列几个，不凑数。
- 池外补搜：仅池内 <20 条时触发；结果模型带 external 标记；单次搜索至多 1~2 次 Search 调用（限速 30 次/分，单人够用）。
- 追问上下文**无状态**：服务端不建会话表、不落库；每轮追问由前端把上一轮意图（JSON，含 filters/unsupported）随新输入回传，服务端只做"旧意图＋新输入 → LLM 合并 → 新意图 → 重跑"；刷新页面状态即清零。追问搜空时的上一轮结果保留由前端随表单回传的上一轮结果摘要（full_name＋理由＋池内外标记）重渲染，不额外调 LLM。
- 成本：每次搜索 1~3 次 DeepSeek 调用；20 条＋候选 50 后单次 token 消耗约为原 10 条口径的两倍（2026-08-19 本人拍板接受）；不建搜索缓存（重复搜代价可接受，痛点真出现再议）。
- 关注闭环：复用 `ingest_followed_repo`（source='follow'＋基线快照）；已在池/已关注的池外行不显示关注入口（full_name 查库判定）。
