# 共识文档 —— GitHub 雷达系统（v3）

> 确认状态：**已确认**　确认日期：2026-08-09　版本：v3（grilling 逐问确认，8 个决策点全部落定；v3：§7 翻译口径重写——全池覆盖＋变更自动重译＋手动触发，2026-08-10 本人拍板）
> 本文档是需求与技术的共识基准，《需求清单》《架构决策记录》以此为详细来源；冲突时以本人最后确认的版本为准。

## 1. 项目定位与核心目标
- **形态**：全自动服务，部署于已有云服务器（4核8G）。
- **核心目标**：扩展技术知识面，填充个人知识库，为未来项目选型提供参考，**不追求追突发黑马**。
- **使用范围**：仅限单人使用。

## 2. 数据源
- **数据源**：GitHub 官方 API（非 Trending 爬虫），以保障稳定性。
  - **每日星数更新**：GraphQL API `nodes(ids:)` 批量接口（每请求 100 个仓库）。
  - **Search API**：仅用于初始快照的分片枚举与每日发现池查询。
- **速率限制（已实测核正）**：REST 核心接口 5000 次/小时；Search API 单独限 30 次/分钟；Search 单查询最多返回 1000 条结果。个人访问令牌一枚，配额预算见 §4。
- **数据获取**：每日定时抓取跟踪池内仓库星数，存储星数历史，用于计算增量。

## 3. 筛选策略（热度判定）
- **时间粒度组合**：
  - **周度报告（主力）**：每周日生成，基于过去 7 天新增星数增量排序。
  - **季度回顾（辅助）**：每季度生成一次，基于过去 90 天累计增量排序。
  - **总热度备查**：总星数排名实时可查，不主动推送。
- **候选池**：本地跟踪池（见 §4 分层池），不做全站海选。
- **分类展示（全部本地 SQL 计算，零 API 成本）**：
  - **语言分类**：按 GitHub 主语言字段独立排名，每语言 Top 30。指定 6 语言 `Java, Go, Rust, TypeScript, JavaScript, Python`；language 为 null 或不在 6 种之内 → **"其它语言"** 榜（Top 30）。
  - **主题分类**：按**封闭主题词表**（YAML 配置，见《架构决策记录》附录，实施时本人过目封板）匹配仓库 topics：命中 ≥1 词 → 进该主题榜（Top 30）；命中多个主题 → 多榜重复出现；零命中 → **"其他"** 主题榜（Top 30）。接受副作用：无 topics 项目全部沉入"其他"榜，不做 AI 二次归类。
- **筛选门槛**：入池门槛见 §4（≥1000 星核心池 + 发现池）；榜单不设额外门槛。
- **不足 30 个时**：有多少列多少。
- **重复出现策略**：允许同一项目在多个分类榜单中重复出现。
- **周增量口径**：
  - 基准：本周日快照星数 − 7 天前快照星数；每日快照固定 UTC 00:00。
  - 端点缺失：向另一侧滑动取最近可用快照（窗口 5~9 天均接受），报告标注实际窗口天数；中间天数缺失不影响（星数为单调读数，只看两端）。
  - **新入池项目首周缺席增量榜**（无 7 天前基线，且星数历史无法回填），第二周起正常参与。
  - 负增量正常参与排序（自然沉底）；连续 404 的仓库标记 dead，剔除榜单、保留历史。
- **阅读量**：每周约 200~400 个项目（17 分类 × Top 30，含重复），已确认可接受。

## 4. 初始化与分层跟踪池（v2 重写）
- **已实测事实**（2026-08-09，Search API）：全站 ≥100 星仓库 **472,281** 个，≥1000 星 **63,921** 个。全量跟踪 ≥100 星每日需 47 万次请求，超 REST 全天预算 4 倍，物理不可行——**放弃"全量 ≥100 星"方案**。
- **核心跟踪池**：≥1000 星（约 6.4 万个）。首次部署经 Search 分片枚举 + GraphQL 批量抓取当前星数，存基准快照；之后每日 GraphQL 批量更新（约 640 请求/天）。
- **发现池**：每日跑"近 90 天创建、stars>50"类增量搜索查询，把冒头新项目及时拉进跟踪池，避免新项目熬到 1000 星才被发现（每日请求量数百以内）。
- **已接受代价**：100~999 星且未被发现池捕获的项目上榜前会迟到——与"不追黑马"定位一致。
- **首期周报告**：需等待 7 天后有增量数据，届时正常生成。
- **初始内容填充**：生成"初始全明星榜"（按总星数降序，Top N 由 AI 定），作为首页默认视图，第一份周报生成后替换。

## 5. 消费形式（Web 页面）
- **技术选型**：FastAPI + Jinja2 服务端渲染 + SQLite，部署于已有服务器。
- **访问控制**：Caddy 反代（已有域名，自动 HTTPS）+ Basic Auth；应用内不做用户系统。服务器现状（端口占用/已有服务）实施时探测。
- **展示布局**：
  - 页面两大区块：**语言榜单**（7 块）与**主题榜单**（10 块）；每块按周增星数降序 Top N（N=30，不足按实际）。
  - 项目卡片：仓库名、描述（英文+中文翻译）、本周增星数、总星数、语言、链接、**推荐理由**（AI 生成，每周刷新）、标签、关注按钮。
- **交互功能**：
  - **关注 = 动态入池**：点击关注任意仓库即抓一次当前星数作基线快照并加入每日跟踪；页顶"我的关注"区展示当周增量；取消关注不踢出跟踪池。预计关注 ~50 个。
  - **分类打标**：每个仓库可打任意自定义标签（字符串），页面按标签筛选；标签只能打在池内仓库（榜单/关注列表中见过的），无额外数据逻辑。
- **历史周次**：周报可回看历史期次。

## 7. 数据处理与 AI 增强（v3 重写，2026-08-10 本人拍板）
- **模型**：DeepSeek（deepseek-chat）。初始总成本 < ¥1，稳态每周可忽略。
- **简介翻译（全池覆盖＋变更自动重译＋手动触发）**：
  - **覆盖**：跟踪池**全部仓库**（含 dead 仓，2026-08-10 本人拍板）——有英文简介且无中文的，每日 job 批量补译，目标是"全看中文"。（v2"只译首次进入展示面"作废：跟踪池实际仅 500+ 仓，全译成本可忽略。）
  - **更新**：不再"只译一次"——每日采集比对 description_en，原文变更即更新原文并清掉旧译文，当日 job 自动重译（自愈，无需人工）。
  - **中文判定**：任一 CJK 汉字即视为已有中文，跳过翻译、保持 NULL（展示回退英文原文）。（v2"占比过半存原文"作废：中英混排简介会误判送译。）
  - **手动触发**：行内面板"重新翻译"按钮（单个强制重译，覆盖漏译/译文陈旧/译得差）＋页面"补译全部缺失"按钮（批量，后台执行、防重复触发）。
- **推荐理由**：每周报告生成时，对当周上榜项目按**项目**生成一次（跨榜复用同一推荐语），输入为仓库名/简介/语言/topics/本周增量/总星数等元数据（**不抓 README**），输出 2~3 句中文，每周重新生成。
- **降级**：AI 调用失败不阻塞出榜——无翻译则展示英文原文，无推荐语则省略该行。

## 8. 运维与故障容忍
- **故障容忍**：连续 3 天失败静默重试，允许数据空洞（由 §3 滑动窗口口径消化），不主动报警。
- **备份**：每日快照任务完成后 `sqlite3 .backup` + gzip，本地轮转保留 14 份；每周 scp 一份到异机（本人电脑或对象存储）。历史星数与关注/标签数据不可再生，翻译与推荐语可再生。
- **维护投入**：vibe coding，无具体时间限制。
